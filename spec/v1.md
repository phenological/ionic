# .ion format — version 1

The exact byte layout of the `.ion` format at `format_version = 1`. Reader and writer must match it byte for byte.

- `format_version` (header byte 9) is `1`. The reader uses it to pick the layout.
- Status: frozen (package `0.2.2`). The bytes do not change within version 1.
- A breaking change raises `format_version`. The reader rejects any version above `1`, and rejects any unknown codec or dtype value — such a file was written by a newer build.

All integers are little-endian. The header is written last.

## Design rules

- Source-independent. The file stores items, arrays, summaries, metadata, and offsets into itself. It does not record where the data came from.
- Metadata is keyed by CV accession. Structural attributes with no CV term use Ionic's own attribute vocabulary.
- The header holds the real offsets and lengths. Physical order is fixed, but the reader trusts the header, not adjacency.

## Section map

| Letter | Role                                                       | Shape                                  |
| ------ | ---------------------------------------------------------- | --------------------------------------- |
| header | file header                                                | fixed 1024 bytes                       |
| —      | spectrum array blocks (`packed_spectra`)                   | block container, directory at tail     |
| —      | chromatogram array blocks (`packed_chroms`)                | block container, directory at tail     |
| A0     | spectrum m/z-window directory — window → A3 addresses      | u32 columns (CSR), compressed          |
| A1     | spectrum fast-filter summary (`spec_summary`)              | fixed 80-byte record per spectrum      |
| A2     | spectrum array index (`spec_entries`)                      | fixed 16-byte record per spectrum      |
| A3     | spectrum array address table (`spec_array_addresses`)      | fixed 32-byte record per array         |
| B0     | chromatogram window directory — window → B3 addresses      | u32 columns (CSR), compressed          |
| B1     | chromatogram fast-filter summary (`chrom_summary`)         | fixed 80-byte record per chromatogram  |
| B2     | chromatogram array index (`chrom_entries`)                 | fixed 16-byte record per chromatogram  |
| B3     | chromatogram array address table (`chrom_array_addresses`) | fixed 32-byte record per array         |
| C      | spectrum metadata (`spec_meta`)                            | grouped, directory at tail             |
| D      | chromatogram metadata (`chrom_meta`)                       | grouped, directory at tail             |
| E      | global metadata (`global_meta`)                            | one compressed section                 |

A1, A2, A3 are the per-spectrum tables (summary, index, addresses). Read them in order to rebuild one spectrum: `A1 → A2 → A3`. A0 is the m/z-window directory — the cross-spectrum index an extracted-ion read enters first, then it reads `A1` for rt and `A3` for blocks: `A0 → A1 → A3`.

Physical order: header, packed_spectra, packed_chroms, A1, A2, A3, B1, B2, B3, C, D, E, A0, B0, trailer. The reader trusts header offsets, not this order. Every section starts on an 8-byte boundary. A1/A2/A3/B1/B2/B3 are stored with the file codec when the compression codec (header byte 11) is zstd, and stored raw when it is none. A0/B0 are compressed with the file codec when compression is on.

## Version

`crates/parser/src/ion/version_generated.rs` (generated by `make sync` from `config.json`, do not hand-edit) defines:

```
CURRENT_VERSION        = 1
MIN_SUPPORTED_VERSION  = 1
MAX_SUPPORTED_VERSION  = 1
```

`Header::write` always writes `1`. `Header::parse` calls `allow_version` (`format.rs`), which accepts `1`. Any other value is a hard read error (`IonError::UnsupportedFormatVersion`).

## Metadata columns (C, D, E)

C (spectrum metadata), D (chromatogram metadata), and E (global metadata) share one column layout. Every CV parameter becomes one row. C is split into fixed groups of `metadata group size` (8192) items with group-local value pools; D is split the same way; E is one ungrouped section. The full framing is in "C / D — grouped metadata" and "E — global metadata" below.

The column order, written by `serialize_group` (C and D) and `write_packed_meta` (E) in `crates/parser/src/ion/encoder/utilities/meta_collector/grouper.rs`, is:

| Column | Type | Length | Meaning |
| ------ | ---- | ------ | ------- |
| `CI` local index offsets | u32 | g + 1 | row slice `CI[i]..CI[i+1]` for item `i` |
| `MOI` owner ids | u32 | n | owner node id — which element owns this row |
| `MPI` parent ids | u32 | n | parent node id — with `MOI`, rebuilds the element tree (see Node ids below) |
| `MTI` tag ids | u8 | n | which kind of element the row sits in (spectrum, scan, precursor, …) |
| `MRI` CV ref codes | u8 | n | CV vocabulary: `0` MS, `1` UO, `2` NCIT, `3` PEFF, `4` ATTR, `5` IMS, `255` none |
| `MAN` CV accession numbers | u32 | n | numeric tail of the CV term (e.g. `1000285` for `MS:1000285`) |
| `MURI` unit CV ref codes | u8 | n | CV vocabulary for the unit, same codes as `MRI` |
| `MUAN` unit CV accession numbers | u32 | n | numeric tail of the unit CV term |
| `VK` value kinds | u8 | n | `0` numeric, `1` string, `2` empty |
| `VN` numeric values | f64 | numeric_count | f64 pool, in row order (see Rebuilding VI and VOFF) |
| `VLEN` string lengths | u32 | string_count | byte length of each string, in row order |
| `VS` string bytes | u8 | sum of `VLEN` | concatenated UTF-8 bytes, same order as `VLEN` |

`n` = `meta_count` (rows in the group or section). `g` = items in the group. For E, `items` is the whole section, so `CI` has length `items + 1`.

Two columns are not stored: `VI` (value indices) and `VOFF` (string offsets). There is no placeholder and no zero-fill for them. The decoder rebuilds both at read time (see Rebuilding VI and VOFF).

The term name (e.g. "total ion current") is never stored. The reader gets it from the CV vocabulary using `MRI` and `MAN`. The `ATTR` vocabulary (ref code `4`) is Ionic's own; it covers structural attributes with no CV term (id, ref, index, count). Its accession numbers are in `attr_meta.rs`.

## Rebuilding VI and VOFF

The decoder rebuilds `VI` and `VOFF` from the stored columns, in the group prologue, before it builds any `Metadatum`. This is in `crates/parser/src/ion/decoder/utilities/parse_metadata.rs`.

`VI` is a per-kind running counter over `VK`. Walk rows `0..n` in order with two counters, `next_numeric` and `next_string`, both starting at 0:

- `VK[i] == 0` (numeric): `VI[i] = next_numeric`, then `next_numeric += 1`.
- `VK[i] == 1` (string): `VI[i] = next_string`, then `next_string += 1`.
- `VK[i] == 2` (empty): `VI[i] = 0` (unused; there is no pool entry).

(`rebuild_value_indices`.)

`VOFF` is the prefix sum of `VLEN`: `VOFF[0] = 0`; for `k >= 1`, `VOFF[k] = VOFF[k-1] + VLEN[k-1]` (`rebuild_string_offsets`).

A numeric row then reads `VN[VI]`. A string row reads `VS[VOFF[VI] .. VOFF[VI] + VLEN[VI]]`.

This is correct because of one rule the writer follows: **the value pool is row-parallel — one pool entry per row of that kind, appended in row order, with no deduplication and no reordering.** `serialize_group` builds `VN` and the string pool by walking the rows once and pushing to the matching pool on every numeric or string row; it never reuses an existing pool entry. So `VI` is just a counter and `VOFF` is just a prefix sum, with no stored lookup table.

This rule is normative. If a future writer makes two rows with the same value share one pool entry (deduplication), `VI` stops being a counter and must be stored again. That is a different layout and needs a new `format_version`; the "rebuild from `VK`" rule would produce wrong indices instead of failing, so it cannot be a variant of version 1.

## Node ids: reset and remap

**Encoder (C and D): each item's local node ids start at 2.** `TraversalContext::reset_for_item` (`meta_collector/mod.rs`) runs at the top of `MetaCollector::add_item` for every spectrum and every chromatogram — not just the first item in a group. It resets the node-id counter to `FIRST_LOCAL_ITEM_NODE_ID` (2). The shared list node (the `<spectrumList>`/`<chromatogramList>` element) keeps id `1` and is touched once, on the first item of a group. So inside one group, item 0's rows use ids `2, 3, 4, …`, item 1's rows also start at `2`, and so on. Ids are unique within one item (plus the shared `1`), not across items.

**Decoder (C and D): ids are remapped to group-unique ids in the prologue.** `MetaColumnLayout::ids_reset` is `true` for C and D, so `parse_metadata` runs `restore_group_unique_ids` after `validate_children_index` and before building any `Metadatum`:

1. `stride = 1 + max(all stored MOI and MPI values)` over the whole group.
2. For item `i` (found from the `CI` row range), `item_base = i * stride` (checked multiply).
3. Each id in that item's `MOI`/`MPI` rows: id `1` (the shared list node) stays `1`; any other id becomes `item_base + local_id` (checked add).

This runs once per group, on `MOI` and `MPI`, before the row loop. So every later step (`to_mzml`, `children_lookup`, the `spectra.rs` builders) sees group-unique ids, exactly as before. The reset and remap are invisible past the prologue.

**E is never reset and never remapped.** `pack_global_meta` (`encoder/.../schema.rs`) writes E through `context.alloc()` and never calls `add_item`, so `reset_for_item` never runs for E and E's node ids keep counting up across the section. On read, `IonReader::global_metadata()` (`decoder/decode/spectra.rs`) is the only caller that reads E, and it builds the layout with `.without_ids_reset()`, so E parses with `ids_reset = false` and uses `MOI`/`MPI` as stored. `without_ids_reset()` clears only `ids_reset`; E still rebuilds VI and VOFF the same way.

## A0 — spectrum m/z-window directory

A0 is the m/z index: it maps an m/z value to the array segments that hold it, so an extracted-ion read (one m/z window across all spectra) opens only those blocks instead of scanning every spectrum. A window is `floor(mz / target_mz_window)` (width at header offset 24). The header points to A0 (off/len at 32/40) and holds its CRC32 at offset 968. A0 is compressed with the file codec when compression is on; the CRC32 covers the stored bytes.

A0 holds pointers only — A3 stays the single source of truth for block, offset, and dtype. The body is monotonic `u32` arrays stored column-wise (CSR, like A2→A3):

| Part              | Type | Length           | Meaning                                               |
| ----------------- | ---- | ---------------- | ------------------------------------------------------ |
| window_count      | u32  | 1                | number of windows (`starts` has window_count+1 slots) |
| entry_count       | u32  | 1                | number of window entries                              |
| starts            | u32  | window_count + 1 | `starts[b]..starts[b+1]` is window b's entry slice    |
| spectrum_index    | u32  | entry_count      | owning spectrum, strictly ascending within a window    |
| mz_address        | u32  | entry_count      | A3 row of that window+spectrum's m/z segment          |
| intensity_address | u32  | entry_count      | A3 row of the paired intensity segment                |

One entry per (window, spectrum) that stores m/z in that window. Each column rises within a window, so the codec compresses it well. An empty A0 (no windowed m/z arrays) is a zero-length section. `rt` is not stored here; the reader reads it from `A1[spectrum_index]`.

A0 is required for m/z-range and extracted-ion reads; there is no full-array fallback. The writer guarantees A0 exists by rejecting any spectrum whose m/z array is not sorted ascending. The reader checks the CRC32, then the structure (`starts` runs `0 → entry_count` and never drops, `spectrum_index` strictly rises within a window, every address is in range). A missing, CRC-failed, or malformed A0 is an error, not a silent wrong answer — re-encode the file from its mzML source with `ionic convert`.

To read `[query_low, query_high]`: for each window in `floor(query_low/width)..=floor(query_high/width)`, take its entry slice, read the m/z and intensity A3 rows, decode those blocks, and cut to range. Finite rt is stored ascending (the writer rejects any spectrum whose rt drops below the previous one, the same way it rejects unsorted m/z), so when every spectrum has a finite rt, a window's entry slice is rt-ascending in `spectrum_index` and an rt range is found by binary search over `A1[spectrum_index].rt`. A spectrum may lack rt (non-finite, e.g. SRM); that turns off the binary-search path for the file, and the reader scans each window's slice instead. The window width is an integer number of m/z units; the writer rounds it before storing, so the reader recomputes the same window a value was stored in.

## A1 — spectrum fast-filter summary (80 bytes)

A1 is a rebuildable cache: every used field comes from the spectrum's metadata in C under its CV accession, so A1 can be rebuilt from C. The header holds A1's CRC32 at offset 972.

| Offset | Size | Field             | Type / sentinel                                   | State |
| ------ | ---- | ----------------- | --------------------------------------------------- | ----- |
| 0      | 8    | rt                | f64, raw value in the unit at byte 54             | used  |
| 8      | 8    | base_peak_mz      | f64                                                | used  |
| 16     | 8    | selected_ion_mz   | f64                                                | used  |
| 24     | 8    | base_peak_int     | f64                                                | used  |
| 32     | 8    | total_ion_current | f64                                                | used  |
| 40     | 1    | ms_level          | u8                                                 | used  |
| 41     | 1    | polarity          | u8 (0 unknown, 1 positive, 2 negative)             | used  |
| 42     | 4    | position_x        | u32, 0 = unknown                                   | used  |
| 46     | 4    | position_y        | u32, 0 = unknown                                   | used  |
| 50     | 4    | position_z        | u32, 0 = unknown                                   | used  |
| 54     | 1    | rt_unit           | u8 (0 unknown, 1 second, 2 minute, 3 millisecond)  | used  |
| 55     | 25   | tail              | zero                                               | free  |

Every used field keeps its offset. The free tail may gain optional fields (see Extensibility). Readers ignore tail slots they do not know; writers zero any tail bytes they do not set.

## A2 — spectrum array index (16 bytes per spectrum)

A2 maps each spectrum to its array addresses in A3. The header holds A2's CRC32 at offset 976.

| Offset | Size | Field                         |
| ------ | ---- | ------------------------------ |
| 0      | 8    | first array address (into A3) |
| 8      | 8    | array address count           |

## A3 — spectrum array address table (32 bytes per array)

A3 holds one record per array segment. The header holds A3's CRC32 at offset 980.

| Offset | Size | Field                                                                           |
| ------ | ---- | --------------------------------------------------------------------------------- |
| 0      | 8    | element offset (inside the block)                                               |
| 8      | 8    | element count (elements in this segment)                                        |
| 16     | 4    | block id (into the container directory)                                         |
| 20     | 4    | array accession (numeric tail of the CV term)                                   |
| 24     | 1    | dtype (see codes)                                                               |
| 25     | 1    | array filter (PackingId, see codes)                                             |
| 26     | 4    | encoded length (0 = fixed-width; >0 = variable-length byte count)               |
| 30     | 1    | continues_previous_segment (0 = new array, 1 = next segment of the array above) |
| 31     | 1    | array accession CV ref code (same codes as C/D `MRI`: 0 MS, 1 UO, …, 255 none)  |

The accession at byte 20 is only the numeric tail; byte 31 names its vocabulary, so the array type is fully qualified without assuming MS. All segments of one array share the same CV ref code.

Window membership is not stored per segment. The window → segment mapping lives only in A0, so a range or extracted-ion read goes through A0, and a whole-spectrum read goes through `A1 → A2 → A3` without needing it.

Each address resolves on its own from block id, element offset, and element count. The writer emits one address per stored segment and does not deduplicate arrays.

One array may be stored as several segments in a row: the first has `continues_previous_segment = 0`, each later segment has `1`. To rebuild the array, read the segments in order and join them. A leading `1`, a value above `1`, or a segment whose dtype or filter differs from the first is an error. All segments of one array share the same accession, dtype, and filter.

## B0 — chromatogram window directory

B0 is the chromatogram version of A0 and uses A0's layout, but chromatograms are not split by m/z window: every chromatogram is a single entry under window 0. The header holds B0's CRC32 at offset 984.

## B1 — chromatogram fast-filter summary (80 bytes)

B1 is the chromatogram version of A1 — a rebuildable cache derived from D. The header holds B1's CRC32 at offset 988.

| Offset | Size | Field                | Type / sentinel | State |
| ------ | ---- | -------------------- | ---------------- | ----- |
| 0      | 8    | lowest_mz            | f64              | used  |
| 8      | 8    | highest_mz           | f64              | used  |
| 16     | 8    | lowest_wavelength    | f64              | used  |
| 24     | 8    | highest_wavelength   | f64              | used  |
| 32     | 8    | lowest_ion_mobility  | f64              | used  |
| 40     | 8    | highest_ion_mobility | f64              | used  |
| 48     | 1    | polarity             | u8               | used  |
| 49     | 31   | tail                 | zero             | free  |

Future fields, not yet written and not yet fixed to an offset: `precursor_mz`, `product_mz` (both f64, NaN = unknown). They become `used` only when the writer fills them and this table gives them an offset.

B2 (16 bytes per chromatogram) and B3 (32 bytes per array) are the chromatogram versions of A2 and A3 and mirror them exactly.

## Array containers

Layout: `[block][block]…[block][block directory]`. The order of blocks inside the payload is unspecified; the block directory is authoritative and a reader must resolve every block through it rather than assuming adjacency or that block ids ascend with byte offset. Blocks are grouped by array type, element stride (1, 2, 4, or 8 bytes), and m/z window. A block fills to the target block size, then seals. An array larger than the target gets its own block. Each block is compressed on its own when compression is on.

A spectrum's m/z and intensity arrays are cut into ordered m/z windows: the m/z axis is split into fixed-width windows, and each window's slice becomes one A3 segment (first segment `continues_previous_segment = 0`, each later window `1`). The window index of an m/z value is `floor(mz / width)`, where `width` is the target m/z window at header offset 24 (u32, m/z units; library default 100, CLI convert default 250). Same-window slices from different spectra share blocks (a block holds one array type, one stride, one window), so a range read opens only the blocks of the windows it overlaps. The reader finds them by computing the window indices of its m/z range with the same `width`, then looking those windows up in A0. The writer rounds `width` to an integer before storing it, so the reader recomputes the exact window each value was placed in.

Block directory entry (32 bytes), one per block:

| Offset | Size | Field                                        |
| ------ | ---- | --------------------------------------------- |
| 0      | 8    | payload offset (relative to container start) |
| 8      | 8    | payload size                                 |
| 16     | 8    | uncompressed length                          |
| 24     | 4    | crc32 of the stored payload                  |
| 28     | 4    | reserved, zero                               |

Each entry has its own payload crc32, but the entry's offset and size are not covered by it. The whole directory is protected by one crc32 over all its bytes, stored in the header (1000 for spectra, 1004 for chromatograms). The reader checks it before it trusts any offset, so a corrupted offset cannot resolve to a different valid block. An empty container has a zero-length directory and a crc32 of `0`.

## C / D — grouped metadata

Layout: `[group payload]…[group payload][group directory]`. Items are split into fixed groups of `metadata group size` (8192) items. Each group is serialized, then compressed on its own when compression is on. A group's value pools are local — no pool crosses a group boundary. Node ids are group-local and, within a group, per-item (see Node ids).

Group directory entry (32 bytes), one per group:

| Offset | Size | Field                                      |
| ------ | ---- | -------------------------------------------- |
| 0      | 8    | payload offset (relative to section start) |
| 8      | 8    | payload size                               |
| 16     | 8    | uncompressed size                          |
| 24     | 4    | crc32 of the stored payload                |
| 28     | 4    | reserved, zero                             |

Decompressed group body starts with a 12-byte header:

| Offset | Size | Field                           |
| ------ | ---- | --------------------------------- |
| 0      | 4    | meta_count (rows in this group) |
| 4      | 4    | numeric_count                   |
| 8      | 4    | string_count                    |

Then the column arrays from "Metadata columns", in that order. `VI` and `VOFF` are not stored; the decoder rebuilds them.

## E — global metadata

One compressed section. It does not scale with item count, so it is not grouped. It starts with a 32-byte counts header, then the same column arrays as a group body (for the whole section, with `CI` of length `items + 1`). E's node ids are never reset or remapped: `MOI`/`MPI` are used as stored.

Counts header (32 bytes): nine u16 values in this order — file descriptions, ref param groups, samples, instrument configs, software, data processing, acquisition settings, cvs, runs — then 14 reserved zero bytes.

## Codes

Compression codec (header byte 11): `0` none, `1` zstd. An unknown codec id is a breaking change; the reader fails and needs a new `format_version`.

dtype (A3/B3 byte 24): `1` f64, `2` f32, `3` f16, `4` i16, `5` i32, `6` i64. An unknown dtype is a breaking change; the reader fails and needs a new `format_version`.

PackingId (array filter): `0` raw, `1` byte shuffle, `2` delta shuffle. Two fields use these codes. Header byte 13 (`default array filter`) is the file-wide default the writer picks. A3/B3 byte 25 (`array filter`) is the filter for that one segment. The reader reads byte 25 per segment to unpack it. The two fields are chosen on their own and need not match.

## Integrity and validation

- The file starts with the signature `IONIC\0\0\0` and ends with the trailer `\0\0\0CINOI`.
- The header crc32 at offset 1020 covers header bytes 0..1020.
- The 13 section checksums sit at the header tail (968..1020): A0 at 968, A1 at 972, A2 at 976, A3 at 980, B0 at 984, B1 at 988, B2 at 992, B3 at 996, spectrum block directory at 1000, chromatogram block directory at 1004, C at 1008, D at 1012, E at 1016.
- C, D, E each have a crc32 in the header over their whole section.
- Every block and every group carries its own crc32.
- Each block container directory has one crc32 over all its bytes, in the header (1000 for spectra, 1004 for chromatograms). The reader checks it on open, before it trusts any block offset.
- A3 and B3 each have a crc32 in the header (980 and 996). They are required for range reads; a failed CRC is an error, not a fallback.
- `total file size` equals the real file length.
- Sections do not overlap, are 8-byte aligned, and sit after the header.
- Reserved bytes at header 14..16 and 432..968 are checked zero on parse; a non-zero byte is an error. A1/A2/A3/B1/B2/B3 are stored raw when the compression codec (header byte 11) is none, and stored with the file codec when it is zstd.
- When the compression codec (header byte 11) is zstd, each of A1/A2/A3/B1/B2/B3's `len_*` header field (56, 72, 88, 120, 136, 152) is the stored (compressed) length, and that section's crc32 covers the stored bytes, not the decompressed bytes. The plain size is not stored; it is derived on read: A1/A2 and B1/B2 from `spectrum_count` and `chromatogram_count` (offsets 256/264), and A3/B3 from `max_address_index` over the decoded A2/B2 index.
- `format_version` must be `0` or `1`. Any other value is a hard read error before any section is touched.

Validation modes:

- Open: cheap directory checks only — directory bounds, each payload ends before its directory, `sum(group uncompressed size)` equals the header total, and each block container directory matches its header crc32. No decompression.
- Random access: decode and checksum only the target group and the target item's blocks.
- Full read: decode all groups and check the row, numeric, and string totals against the header.

## Version 1 limits

- Header item counts (spectra, chromatograms): u64.
- Node ids are group-local and per-item: each item's local ids restart at `2`, so the u32 node-id space never accumulates across the file. Item count is bounded only by the u64 header counts, not by the node-id width.
- Rows, numeric, string counts per section: u32.
- Global counts: u16 (max 65535 each).
- String pool offsets: u32 (max 4 GiB per section), rebuilt at read time, not stored.

## Extensibility

Version 1 grows in one way: **A1/B1 tail fields**. The reserved tail of A1 and B1 may gain optional fields. Rules:

- A1 and B1 are 80 bytes each; every used field keeps its offset.
- Once a tail slot is given an offset, it keeps that offset, type, sentinel, unit, and CV accession forever, and is never reused for another meaning.
- A slot is used, reserved, or free (zero).
- Readers ignore slots they do not know. Writers zero any tail bytes they do not set.

The header reserved area at 432..968 stays checked-for-zero and is off-limits. Any change to bytes 432..968, or to any fixed layout above, is a real format change — a new `format_version` and a new spec file.
